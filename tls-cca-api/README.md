# TLS CCA API

API backend for the Auto Debt Management system, built with Django and Django REST Framework. It provides a robust backend with role-based access control (RBAC) for managing users, customers, sales, and receivables.

## Features

- **User Management:** Secure user registration, authentication (login/logout), and profile management with JWT.
- **Role-Based Access Control (RBAC):** Fine-grained permission system to control access to different API endpoints based on user roles.
- **Customer Relationship Management (CRM):** Manage customer data and portfolios.
- **Sales Management:** Track credit sales.
- **Receivables Management:** Manage debts and recovery processes.
- **Reporting:** Generate reports on various aspects of the system.
- **API Documentation:** Auto-generated API documentation using `drf-spectacular`.

## Getting Started

These instructions will get you a copy of the project up and running on your local machine for development and testing purposes. The V1 API is versioned under `/api/v1/`; the old `/api/...` routes are temporary compatibility aliases.

### Prerequisites

- Python 3.12+
- Poetry for dependency management

### Installation

1.  **Clone the repository:**

    ```bash
    git clone https://github.com/Thrylos77/auto-debt-management.git
    cd auto-debt-management/tls-cca-api
    ```

2.  **Install dependencies using Poetry:**

    ```bash
    poetry install
    ```

3.  **Create a `.env` file:**

    Copy the `.env.example` to a new file named `.env`.

    ```bash
    cp .env.example .env
    ```

    Update the `.env` file with your specific settings, such as `DJANGO_SECRET_KEY`, and email credentials.

4.  **Apply database migrations:**

    The audit application has a real initial migration because RBAC synchronization writes audit events.
    Generate/check the audit migration first, then apply all migrations.

    ```bash
    poetry run python manage.py makemigrations audit
    poetry run python manage.py makemigrations
    poetry run python manage.py migrate
    poetry run python manage.py showmigrations audit
    ```

    For an existing database that predates Django migrations, compare the live schema before using `--fake-initial`; do not fake a baseline blindly.

5.  **Create a superuser:**

    ```bash
    poetry run python manage.py createsuperuser
    ```

6.  **Seed initial data (optional but recommended):**

    ```bash
    poetry run python manage.py sync_rbac --strict
    ```

## Running the Application

To run the development server, use the following command:

```bash
poetry run python manage.py runserver
```

The API will be available at `http://127.0.0.1:8000/`.

## Running Tests

To run the test suite, use `pytest`. The following command will run all tests and provide a coverage report:

```bash
poetry run pytest
```

## Vague 2 — RBAC canonique + audit

- `RoleAssignment` et `GroupMembership` sont les tables canoniques et uniques d'assignation RBAC.
- `PermissionResolver` ne lit que ces deux sources canoniques ; l'ancienne relation applicative `User.roles` / `User.groups -> rbac.Group` a été retirée. La relation native `AbstractUser.groups -> auth.Group` reste héritée de Django et n'est pas utilisée par le RBAC applicatif.
- `sync_rbac --dry-run --strict` permet de verifier le registre avant ecriture ; `sync_rbac --strict` applique la source declarative.
- `AuditEvent` est append-only et expose `GET /api/v1/audit/events/` et `GET /api/v1/audit/events/{id}/`. Le hard-delete d’un utilisateur qui possède des événements d’audit est bloqué afin de préserver la traçabilité ; la désactivation doit être utilisée à la place.
- Les metadonnees sensibles sont redigees recursivement avant persistance.
- Le script `start_project.ps1` traite le warning de pagination `UnorderedObjectListWarning` comme une erreur de regression.

## Vague 4 — Lot 6

Le reporting possède désormais les services de dashboard global et de recherche fédérée auparavant situés dans `core`. Les routes V1 historiques restent inchangées.

Les événements internes partagés sont définis dans `core.events`, et les opérations métier sensibles des modules CRM, Sales et Receivables émettent ces événements pour l'audit.

## Finalisation Vague 4 — sécurité et nettoyage legacy

L'API publique applicative est désormais exclusivement exposée sous `/api/v1/`. Les anciennes routes `/api/core/`, `/api/users/`, `/api/roles/`, `/api/groups/`, `/api/crm/`, `/api/sales/`, `/api/receivables/`, `/api/reporting/`, `/api/audit/` et `/api/token/` ne font plus partie du contrat.

Le RBAC utilise uniquement `RoleAssignment` et `GroupMembership`, et le profil de sécurité porte seul l'état 2FA et le secret TOTP chiffré. Les commandes de migration ponctuelle legacy ont été retirées ; les migrations historiques de base de données sont conservées.

Les paramètres de durcissement principaux sont configurés par variables d'environnement : CORS par allowlist, limite de taille des requêtes API, cookies `SameSite=Lax`, COOP, rotation/blacklist des refresh tokens, vérification de révocation JWT et clé JWT dédiée en production.

Avant installation de cette version, ajoutez la dépendance CORS :

```powershell
poetry add django-cors-headers
```

En production, `DJANGO_SECRET_KEY`, `JWT_SIGNING_KEY`, `JWT_AUDIENCE`, `JWT_ISSUER`, `DB_NAME`, `ALLOWED_HOSTS`, `TOTP_ENCRYPTION_KEY` et `AUTH_PUBLIC_BASE_URL` doivent être renseignés. `TOTP_ENCRYPTION_KEY` doit être une clé Fernet dédiée et `AUTH_PUBLIC_BASE_URL` doit utiliser HTTPS. Une modification de `JWT_SIGNING_KEY` invalide volontairement les JWT existants : le retour arrière consiste à restaurer l'ancienne valeur pendant la fenêtre de réversibilité prévue.

Pour générer une clé Fernet locale : `poetry run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`.

Validation finale recommandée :

```powershell
poetry run python manage.py check
poetry run python manage.py makemigrations --check --dry-run
poetry run python manage.py migrate
poetry run python manage.py sync_rbac --dry-run --strict
poetry run python manage.py sync_rbac --strict
poetry run pytest -v -W error::django.core.paginator.UnorderedObjectListWarning
poetry run python manage.py spectacular --file /tmp/tls-cca-openapi.yaml
```

## Vague 5 — Authentification, enrôlement MFA et récupération

La Vague 5 impose l'enrôlement Authenticator (TOTP) avant toute session normale. La connexion standard repose sur mot de passe + TOTP ; l'email reste réservé aux invitations, récupérations et notifications de sécurité. Les récupérations sont séparées entre self-service avec TOTP et procédures administratives pour les cas privilégiés ou la perte du second facteur.

Voir `docs/AUTHENTICATION-LIFECYCLE.md` pour les parcours, endpoints, permissions et contrôles de sécurité.

## Vague 6 — CRM Enterprise

Le CRM conserve son modèle client/portefeuille existant et introduit un cycle de vie explicite, sans exposer de modification d'état libre via `PATCH`.

Lifecycle client : `prospect`, `active`, `suspended`, `inactive`, `blocked`, `archived`. `is_active` reste conservé pour compatibilité et reste synchronisé par les opérations métier explicites.

Nouvelles capacités V1 :

- `POST /api/v1/crm/customers/{id}/suspend/`
- `POST /api/v1/crm/customers/{id}/block/`
- `POST /api/v1/crm/customers/{id}/archive/`
- `GET /api/v1/crm/customers/{id}/timeline/`
- `POST /api/v1/crm/customers/duplicates/check/`

La déduplication est une aide à la décision : elle normalise les identifiants, retourne des candidats et des niveaux de confiance et ne supprime jamais automatiquement un client.

Le profil Customer 360 est enrichi avec les coordonnées structurées (ligne d’adresse, quartier, ville, région, code postal, pays et code pays), les canaux de contact et des informations professionnelles. Les personnes physiques disposent de données d’identité, naissance, document et activité professionnelle plus détaillées ; les personnes morales disposent des informations légales, fiscales, d’activité et de représentant légal. L’ancien champ `address` reste conservé pendant la période de compatibilité.

Les modèles CRM sont séparés en `crm/models/customer.py` et `crm/models/portfolio.py`, avec `crm/models/__init__.py` comme façade de compatibilité pour les imports existants.

La timeline agrège l'audit existant sans dupliquer `AuditEvent` dans CRM. Son accès est protégé par `customer.timeline` et le périmètre du portefeuille.

Les affectations de portefeuille restent journalisées dans `PortfolioTransfer`; les mutations vérifient désormais qu'un portefeuille inactif ne peut pas être réattribué et que le portefeuille est verrouillé pendant l'opération.

La documentation OpenAPI prend en charge l'authentification JWT renforcée via une extension dédiée, et la génération de schéma n'exécute pas les contrôles métier de permission des vues pendant l'introspection. Les serializers dynamiques utilisent des descriptions de type explicites.
